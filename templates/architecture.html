Google Cloud Architecture Blueprint

Enterprise Cloud Computing System Architecture

Comprehensive breakdown of how Google Cloud Run, Cloud Storage, Vertex AI / Gemini Vision, Cloud Firestore, BigQuery, and Looker Studio interconnect.

Step 1 • Compute (CaaS)

Google Cloud Run

Application & API Gateway

  • Serverless Container as a Service (CaaS) running FastAPI.
  • Automatically scales from 0 to 1,000+ instances during campus emergency spikes.
  • Zero idle infrastructure cost ($0.00 scale-to-zero).
Step 2 • Object Storage

Cloud Storage (GCS)

Incident Evidence Ingestion

  • Globally distributed blob/object storage bucket.
  • Stores high-resolution incident images uploaded by students.
  • Pre-signed secure URLs prevent unauthenticated media exposure.
Step 3 • Multimodal AI

Vertex AI / Gemini

Hazard Triage & Vision Engine

  • Multimodal visual inspection of damaged equipment and safety risks.
  • Extracts category, OSHA severity rating, and recommended repair procedure.
  • Replaces manual human triage with sub-second AI diagnostics.
Step 4 • OLTP Database

Cloud Firestore

Operational Ticket Storage (OLTP)

  • Serverless NoSQL document store for real-time ticket tracking.
  • Sub-millisecond writes for incident registration and dispatch updates.
  • ACID transactions ensure consistent Kanban board state transitions.
Step 5 • Data Warehouse

Google BigQuery

Analytical Engine (OLAP)

  • Petabyte-scale serverless cloud data warehouse.
  • Computes campus breakdown heatmaps, Mean Time to Resolution (MTTR), and trends.
  • Separates heavy analytical SQL from operational ticket writes.
Step 6 • BI Visualization

Google Looker Studio

Executive BI Reporting

  • Direct SQL connector to BigQuery analytical fact tables.
  • Interactive scorecards, department pie charts, and breakdown heatmaps.
  • Shareable live reports for university leadership and facility heads.

Architectural Design Decisions & Technical FAQs

Engineering rationale behind service selection, data pipeline design, and separation of concerns.

Why use Cloud Run over Google Compute Engine (VMs)?

Compute Engine requires manual VM provisioning, OS security patching, and billing 24/7 even during idle night hours. Cloud Run is serverless: it charges strictly per millisecond of compute used and scales to zero instances when no student incidents are being filed.

Why separate Cloud Storage (GCS) from Cloud Firestore?

Firestore is a NoSQL document database optimized for lightweight JSON metadata (max 1MB per document). Storing multi-megabyte binary images directly in Firestore would drastically degrade query latency and inflate costs. Cloud Storage (GCS) is designed specifically for unstructured blob storage, while Firestore stores the metadata and image reference pointers.

Why use Vertex AI / Gemini API instead of self-hosting a YOLO / ResNet model?

Self-hosting computer vision models requires provisioning expensive GPU-enabled virtual machines (such as NVIDIA T4 or A100 instances) which cost hundreds of dollars monthly. Google Vertex AI / Gemini provides Model as a Service (MaaS)—we pay strictly per token/request, eliminating all GPU cluster maintenance while gaining multi-modal reasoning.

Why separate Firestore (OLTP) from BigQuery (OLAP)?

Firestore (OLTP) is engineered for high-concurrency, single-record lookups and updates as technicians change ticket states on the Kanban board. Running complex analytical aggregations (e.g. Mean Time to Resolution across 50,000 incident events) on Firestore would exhaust read quotas. BigQuery (OLAP) utilizes columnar storage and Massively Parallel Processing (MPP) to return complex analytical queries across millions of rows in seconds.

BigQuery Analytical SQL Queries

The SQL logic powering the campus breakdown heatmaps, resolution velocity, and safety metrics.

SQL Query 1: Mean Time to Resolution (MTTR) & Incident Velocity 
-- BigQuery MTTR & Velocity Analysis
SELECT 
    department,
    COUNT(incident_id) AS total_incidents,
    COUNTIF(severity = 'Critical') AS critical_hazards,
    ROUND(AVG(TIMESTAMP_DIFF(resolved_at, created_at, MINUTE)) / 60.0, 2) AS avg_resolution_hours,
    ROUND(COUNTIF(status = 'Resolved') * 100.0 / COUNT(incident_id), 1) AS resolution_rate_pct
FROM 
    `college-events-cc.campus_incidents_analytics.incident_events`
GROUP BY 
    department
ORDER BY 
    total_incidents DESC;
SQL Query 2: Campus Building Incident Heatmap & Recurring Risk Analysis 
-- BigQuery Building Breakdown Heatmap
SELECT 
    building,
    category,
    COUNT(1) AS failure_frequency,
    ARRAY_AGG(room ORDER BY created_at DESC LIMIT 3) AS frequent_failure_locations
FROM 
    `college-events-cc.campus_incidents_analytics.incident_events`
GROUP BY 
    building, category
ORDER BY 
    failure_frequency DESC;
